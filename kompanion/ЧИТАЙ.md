# Компаньон Jellyfin для Nokia E90

Служба рядом с Jellyfin. Отдаёт записи из библиотеки телефону 2007 года,
который не умеет ничего, кроме RTSP: перекодирует на лету в MPEG-4 800x352 и
раздаёт поток по RTP.

Плагином Jellyfin это не является и не будет: плагины там на .NET, а вся
работа здесь -- запуск ffmpeg и разговор по RTSP. Компаньон общается с
Jellyfin по его же HTTP-API, как обычный клиент.

## Из чего состоит

| Файл | Зачем |
|---|---|
| `rtsp-proba.py` | сервер RTSP, запуск ffmpeg, разбор адресов, проверка пропуска |
| `rtp_relay.py` | посредник: переписывает номера пакетов и меток времени, отвечает плееру |
| `sdp-shablon-24.txt` | готовое описание потока на 24 кадра |
| `zapusk.cmd` | все настройки; его и оборачивать службой |
| `token.txt` | **создать на месте**, одна строка `TOKEN=<токен e90>` |

Зависимостей нет ни одной -- только стандартная библиотека Python 3.8+.

### Про `sdp-shablon-24.txt`

Описание потока (SDP) нельзя сочинить: в нём лежит строка настройки
декодера, которую выдаёт сам кодировщик. Собрать её -- значит открыть запись,
перекодировать кусочек и прочитать результат, а это десятки секунд, пока
телефон ждёт ответа.

Но зависит она только от размера картинки и частоты кадров, а они у нас
всегда целевые -- проверено сравнением побайтно. Поэтому описание собирается
один раз на частоту кадров и кладётся рядом файлом `sdp-shablon-<кадры>.txt`.
Здесь лежит готовое на 24 кадра -- самое частое. Для записи с другой частотой
компаньон соберёт своё при первом обращении (один раз, дальше из файла).

Именно это и делает продукт возможным: иначе на каждую серию уходили бы
десятки секунд ожидания.

## Что нужно на машине

* Python 3.8+ -- годится распакованный embeddable, установка в систему не нужна.
* `ffmpeg.exe` и `ffprobe.exe` -- оба; на машине с Jellyfin они уже есть в
  `C:\Program Files\Jellyfin\Server\`. **`ffprobe` обязателен**: им снимается
  длительность записи и настоящая частота кадров. Назначать частоту рукой
  нельзя -- однажды поставили 25 там, где было 24, и ffmpeg дописал 155
  дублированных кадров, по одному в секунду; на телефоне это выглядело как
  запинка раз в секунду, и причину искали долго.
* Права: чтение программы, запись в папку журналов, сеть.

### Доступ к медиа не нужен

Компаньон **не читает файлы библиотеки**. Запись он тянет у самого Jellyfin
по его же HTTP-адресу, с токеном -- то есть видит ровно то, что видел бы
обычный клиент этого пользователя. Значит учётке службы права на папки с
медиа выдавать не надо вовсе, даже на чтение.

### Про распакованный (embeddable) Python

Такая сборка нарочно не добавляет каталог скрипта в пути поиска -- за это
отвечает файл `python38._pth` рядом с `python.exe`. Из-за этого
`from rtp_relay import ...` падает с `ModuleNotFoundError`, хотя файл лежит
рядом. Лечится одной строкой в `python38._pth` -- путь к папке компаньона.

Найдено при установке на .196; на обычном Python такого нет.

## Порты

| Что | Порт |
|---|---|
| разговор RTSP | TCP 8554 (не 554 -- см. `PROBA_PORT`) |
| поток и отчёты | UDP 40000--40063 |

Диапазон узкий нарочно: его пробрасывают на роутере целиком. Шестьдесят
четыре порта -- шестнадцать одновременных сеансов, на сеанс уходит четыре
(данные и отчёты для каждой из двух дорожек).

Порт Jellyfin наружу нужен тоже (8096 по умолчанию), но его компаньон не трогает:
приложение ходит туда само.

## Как телефон попадает сюда из чужой сети

RealPlayer не умеет принимать поток внутри TCP-соединения -- проверено тремя
способами, он просто кладёт трубку. Зато он ведёт себя как положено клиенту
3GPP: сразу после настройки дорожки, **до начала потока**, шлёт нам пакет с
того самого порта, на котором будет слушать. Этим он открывает обратный путь
в своём роутере.

Поэтому компаньон отвечает не на порт, который плеер назвал о себе сам, а
туда, откуда пакет пришёл на самом деле. Меняется при этом **только порт** и
только если адрес совпадает с адресом разговора RTSP: иначе одним поддельным
пакетом поток можно было бы увести на чужую машину.

## Кого пускаем

Записи Jellyfin отдаются только по пропуску -- это токен Jellyfin, который
приложение кладёт в адрес:

```
rtsp://<машина>/jf/<запись>/k<токен>/at<секунда>
```

Компаньон проверяет его у Jellyfin запросом `/Users/Me` и помнит ответ пять
минут. Без годного токена -- `401` ещё на `DESCRIBE`, то есть ffmpeg не
запускается вовсе. Это главный предохранитель: на каждый запрос поднимается
перекодировщик, и без проверки десяток запросов с улицы кладёт машину.

Если Jellyfin недоступен -- не пускаем никого. Его падение не должно
превращаться в открытую дверь.

Поблажка: из домашних подсетей (`127.`, `10.`, `192.168.`, `172.16--31.`)
пускаем и без токена -- ради совместимости со старыми сборками приложения.
Снаружи поблажки нет никогда. Выключается `PROBA_STROGO=1`.

## Настройки

Все в `zapusk.cmd`, в исходниках адресов нет.

| Переменная | Что задаёт |
|---|---|
| `PROBA_PRODUKT=1` | не собирать пробные варианты из файлов-образцов |
| `PROBA_ZAPIS_KOROTKAYA` | запись для пробных вариантов, минут пятнадцать |
| `PROBA_ZAPIS_DLINNAYA` | она же подлиннее, минут сорок -- по ней видно дрейф звука |
| `PROBA_JELLYFIN` | адрес Jellyfin; на его же машине -- `http://127.0.0.1:32400` |
| `PROBA_FFMPEG`, `PROBA_FFPROBE` | полные пути, в PATH их нет |
| `PROBA_TOKEN_FILE` | файл с `TOKEN=` |
| `PROBA_ZHURNALY` | папка журналов |
| `PROBA_PORT` | порт RTSP; ставить 8554, а не 554 -- см. ниже |
| `PROBA_VIDEO_PKT` | предел пакета видео, по умолчанию 1100 байт |
| `PROBA_ZAPOLNIT` | заполнять экран с обрезкой (1) или целый кадр с полями (0) |
| `PROBA_EKRAN` | экран по умолчанию, если приложение своего не назвало |
| `PROBA_PORTS_FROM`, `PROBA_PORTS_TO` | диапазон UDP |
| `PROBA_STROGO=1` | требовать токен ото всех |

## Про размер картинки

Приложение само называет свой экран участком адреса: `/s320x240`. Компаньон по
нему решает, какого размера картинку кодировать и сколько давать на поток --
600 кбит/с на 800x352 у E90, около 200 на обычные 320x240. Отдавать маленькому
экрану большую картинку значит переплачивать килобитами, а на мобильном канале
они оплачиваются потерями, а не чёткостью.

Описание потока собирается на сочетание «частота кадров + экран» и запоминается:
второй телефон с таким же экраном получит готовое, без ожидания.

Старые сборки приложения экран не называли -- для них и для плееров, пришедших
по голому адресу, берётся `PROBA_EKRAN`.

## Почему пакет видео урезан до 1100 байт

По умолчанию ffmpeg набивает пакет видео до 1472 байт полезной нагрузки, а с
заголовками это IP-пакет ровно 1500 -- предел обычной сети. В мобильной сети
предел меньше (обычно 1400--1430), и такой пакет дробится на два: потеря
любого куска убивает пакет целиком, то есть кусок кадра, и картинка держится
рассыпанной до следующего опорного кадра.

Звук от этого не страдает: у него пакет 400 байт -- отсюда и знакомая
картина «изображение сыплется чаще, чем пропадает звук».

1100 байт дают IP-пакет 1128 -- проходит целым везде. Плата: около семидесяти
пакетов в секунду вместо пятидесяти.

Отдельная беда, которой это не лечит: короткие провалы канала. В журнале они
видны как `плеер сообщает: потеряно 98.8% за интервал`. RTP ничего не
переспрашивает, и на стороне сервера тут сделать нечего.

## Журналы

`rtsp.log` -- весь разговор: какой телефон пришёл, что попросил, сколько
пакетов ушло, на что жалуется плеер. `rtsp-ffmpeg.err` -- вывод ffmpeg,
туда смотреть, если в журнале «ffmpeg умер сразу».

Строки, на которые стоит смотреть первым делом:

* `от плеера пришло: 40000=3, 40001=335` -- чётные порты это данные. Нули на
  чётных при работе из чужой сети означают, что обратный путь не открылся.
* `ОТКАЗ: <адрес> просит запись Jellyfin без годного токена` -- кто-то стучится
  без пропуска.
* `посредник N: пакет с ЧУЖОГО адреса` -- либо чья-то ошибка, либо попытка
  увести поток.
* `ПОТОК СТОИТ: за полминуты ни одного пакета` -- ffmpeg жив, а до телефона
  ничего не доходит.
